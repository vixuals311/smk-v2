## Short answer on H5 (read this first)
**The Phase 12 "blank on a trimmed clip" was caused by my own invalid trim, not by a normal trimmed clip.** I set the clip's mark in/out to frames 0–79 (`SetMarkInOut(0, 79)`), but the PNG sequence's frames are numbered 86400…86519 (the media pool item's Start is 86400). The timeline item then reports `GetLeftOffset() = −86400` and the comp gets `RenderEnd = 0`. With a **valid** trim (86400–86479) the same comp reports `RenderStart = 0, RenderEnd = 79`, every product renders, and the Out ends exactly on the trimmed last frame. Details below.

## Things that went wrong (reported even though they are not SMK bugs)
1. **Debug Fuse hung Resolve's start-up.** I added a throw-away modifier Fuse (`SMK2_DbgRange.fuse`, in `docs/phase13_evidence/`) in `Fuses/SMK2dbg/` to read `self.Comp.RenderStart/End`. Resolve then stayed on its splash screen (no main window, no log output for 5+ minutes) on **three** consecutive launches; after I deleted the folder it started normally. I did not find out why (NOT VERIFIED whether the Fuse code or its folder caused it) and did not use it; the Fuse-side values were read through the existing `SMK2_Motion` modifier and a Text+ expression instead. The `launch_resolve` tool also reported "running" while no process existed (it needed a direct start of `Resolve.exe`).
2. **`run_script_unsafe` timeouts / stalled script threads** as in Phase 12: calls longer than ~10 s were killed, and benchmark threads stopped twice (StatCard variants); items were re-run, not interpolated.
3. **My Phase 12 H5 conclusion was wrong** in attributing the blank to trimming in general; corrected above. Phase 12's `docs/PHASE12_RESULTS.md` H5 row should be read together with this document. Nothing in the H5 source fix was needed for valid trims, but the fix is still the right behaviour for a host range of 0 (Q3c).
